# 演習13: オブジェクト指向プログラミングの基礎

## この演習で学ぶこと

- クラス・プロパティ・メソッド・コンストラクタの基本を理解する
- アクセス修飾子(`public`/`private`/`protected`)によるカプセル化を理解する
- 継承(`extends`)の基本を理解する
- 複数のオブジェクトを配列で扱う方法を理解する

## 前提知識

- 演習05(関数の作成)の内容を理解していること
  - 関数の定義方法(引数・戻り値・型宣言)
  - `return` と `echo` の違い
- 演習01〜04で学んだ変数、データ型、条件分岐、繰り返し処理、配列の基本

## 演習内容(要件)

これまでの演習では、サーバーの情報を「変数」や「連想配列」として
バラバラに扱ってきました。この演習では、それらを1つの「クラス」という
設計図にまとめ、「オブジェクト」として扱う方法を学びます。

### 1. `Server` クラスを作る(クラス・プロパティ・コンストラクタ・カプセル化)

サーバー1台分の情報を表す `Server` クラスを作ります。

- プロパティ(データを保持する変数)として、次の3つを **`private`** で持たせます。
  - `$name`(`string` 型): サーバー名
  - `$ip`(`string` 型): IPアドレス
  - `$cpuUsage`(`int` 型): CPU使用率(0〜100の整数)
- コンストラクタ(`__construct`)で、`new Server(...)` するときに
  この3つのプロパティをまとめて初期化できるようにします。
- 次の `getter`(値を取得するためのメソッド)を用意します。
  - `getName(): string`
  - `getIp(): string`
  - `getCpuUsage(): int`
- `getStatus(): string` メソッドを実装します。`$cpuUsage` の値に応じて、
  次のように文字列を返してください。
  - `70` 未満 → `"正常"`
  - `70` 以上 `90` 未満 → `"注意"`
  - `90` 以上 → `"危険"`

プロパティを `private` にすることで、クラスの外から
`$server->cpuUsage = 200;` のように直接書き換えることができなくなります
(カプセル化)。値を読み取りたいときは、必ず `getName()` のような
getterメソッドを経由させる設計にします。

### 2. `DatabaseServer` クラスを作る(継承・`parent::`)

`Server` クラスを **継承(`extends`)** した `DatabaseServer` クラスを
作ります。

- 追加のプロパティとして `$dbEngine`(`string` 型、`private`)を持たせます
  (例: `"MySQL"`、`"PostgreSQL"` など)。
- コンストラクタでは、`parent::__construct(...)` を使って親クラス
  (`Server`)側のプロパティを初期化したうえで、`$dbEngine` を初期化します。
- `getDbEngine(): string` メソッド(getter)を用意します。
- `getInfo(): string` メソッドを実装します。サーバー名・データベース
  エンジン名・IPアドレス・CPU使用率・状態をまとめた、1行の文字列を
  返してください。状態の取得には **`parent::getStatus()`** を使って、
  親クラスのメソッドを呼び出してください。

### 3. 複数のサーバーをオブジェクトの配列としてまとめ、一覧表示する

`Server` や `DatabaseServer` のオブジェクトを **3〜4個** 作成し、
1つの配列にまとめます(少なくとも1つは `DatabaseServer` にしましょう)。

その配列を `foreach` で1つずつ取り出し、サーバーの一覧として
コンソールに表示してください。`DatabaseServer` かどうかは
`instanceof` 演算子で判定し、`DatabaseServer` であれば `getInfo()` を、
そうでなければ `getName()`・`getIp()`・`getCpuUsage()`・`getStatus()` を
組み合わせて表示すると良いでしょう。

## 実行方法

ターミナル(コマンドライン)で、この演習のディレクトリに移動してから以下のコマンドを実行してください。

```bash
# 未完成のひな形を実行してみる(エラーにはならず、TODO部分だけ「まだ実装されていません」等と表示されます)
php practice.php

# 模範解答を実行する
php answer.php
```

`practice.php` の中の `// TODO:` と書かれた部分を自分で実装してから、
もう一度 `php practice.php` を実行し、`answer.php` と同じような結果が出るか確認してみましょう。

構文だけを素早く確認したいときは、次のコマンドも便利です。

```bash
php -l practice.php
```

## ヒント

- プロパティを `private` にすることで、クラスの外から直接書き換えられないようにする
  (カプセル化)のが基本の考え方です。値を読み書きしたいときは、`getName()` のような
  専用のメソッド(getter)を通す設計にすることで、「意図しない値が
  勝手に入ってしまう」といった事故を防げます。
- 継承(`extends`)を使うと、親クラスの機能(プロパティやメソッド)を
  引き継ぎつつ、新しい機能を追加できます。`class DatabaseServer extends Server`
  と書くと、`DatabaseServer` は `Server` が持っている `getName()` などの
  `public` なメソッドを、あらためて書き直すことなくそのまま使えます。
- `parent::メソッド名()` と書くと、親クラスの同名メソッドを呼び出せます。
  子クラスの中で「親クラスがもともと持っていた処理」を利用したいときに使います。
- コンストラクタ(`__construct`)は、`new クラス名(...)` としたときに
  自動的に呼び出される特別なメソッドです。子クラスのコンストラクタの中で
  `parent::__construct(...)` を呼び忘れると、親クラス側のプロパティが
  初期化されないままになってしまうので注意しましょう。
- `instanceof` 演算子を使うと、`$server instanceof DatabaseServer` のように
  「そのオブジェクトが、指定したクラス(またはその子クラス)のインスタンスかどうか」
  を `true`/`false` で判定できます。
- オブジェクトの配列を扱うときも、`foreach ($servers as $server) { ... }` のように、
  今までの配列と同じ書き方で1つずつ取り出せます。

## サーバーエンジニアとの関連

監視対象のサーバーを「オブジェクト」としてモデル化する考え方は、
大規模な監視ツールやインフラ自動化ツールを設計するうえでの基礎になります。

- 実際の監視システムでは、Webサーバー・データベースサーバー・
  ロードバランサーなど、種類の違うサーバーを何十台、何百台と管理します。
  それぞれを「名前・IP・CPU使用率」といった共通の情報を持つ`Server`
  のようなクラスで表現し、データベースサーバー特有の情報(使っている
  DBエンジンなど)は `DatabaseServer` のように**継承した専用クラス**で
  管理する、という設計は、実務のシステムでも非常によく使われる考え方です。
- プロパティを `private` にしてカプセル化することで、「CPU使用率は
  監視スクリプトが取得した値だけがセットされ、他の場所から勝手に
  書き換えられない」という安全性を保証できます。これは、複数人が
  同じコードを触る現場や、長期間保守されるシステムほど重要になります。
- `getStatus()` のように、「生の数値(CPU使用率)」から「正常/注意/危険
  といった人間にわかりやすい状態」を導き出すロジックをクラスの内部に
  まとめておくと、判定基準(しきい値)を変更したくなったときも、
  そのクラスの中の1箇所を直すだけで済みます。これはInfrastructure as Code
  ツールや監視ダッシュボードのアラート判定ロジックにも通じる考え方です。
- サーバーの一覧を配列として扱い、`foreach` でまとめて処理する構造は、
  実際の監視ツールが「登録されているサーバーを順番にチェックして
  レポートを作る」処理の基本形そのものです。

## 発展課題

余裕がある人は、以下にも挑戦してみましょう。

- `Server` クラスをさらに継承した `WebServer` クラスを新しく作ってみましょう。
  追加のプロパティとして `$requestsPerSecond`(1秒あたりのリクエスト数、`int` 型)
  を持たせ、`DatabaseServer` の `getInfo()` と同じように、`WebServer` 独自の
  `getInfo()`(`parent::getStatus()` を使って状態も表示する)を実装してみてください。
  そのうえで、`$servers` 配列に `WebServer` のオブジェクトも混ぜて、
  `Server`・`DatabaseServer`・`WebServer` の3種類が混在した一覧を
  `foreach` で正しく表示できるか試してみましょう
  (`instanceof` の判定を増やす、またはすべてのクラスに共通する
  `getInfo()` を用意する、といった工夫が必要になります)。
