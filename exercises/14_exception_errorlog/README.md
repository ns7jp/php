# 演習14: 例外処理とエラーログ

## この演習で学ぶこと

- `try` / `catch` / `finally` の基本構文を理解する
- `Exception`(や、その仲間である `RuntimeException` など)を継承した、
  独自の例外クラスを作れるようになる
- `throw` を使って、自分で定義したエラー(例外)を発生させられるようになる
- `error_log()` を使って、エラーの内容をログファイルに記録できるようになる
- 「画面にエラーの詳細を出さず、ログに残す」という、実務のサーバー運用で
  とても重要な原則を理解する

## 前提知識

- 演習13(オブジェクト指向プログラミングの基礎)の内容を理解していること
  - `class` によるクラスの定義
  - `extends` を使った継承
  - コンストラクタ(`__construct`)と `$this`
  - `parent::` を使った親クラスの呼び出し
- 演習01〜07で学んだ変数、条件分岐、関数、日時操作(`date()`)の基本

## 演習内容(要件)

これまでの演習では、「ファイルが存在しない」「値がおかしい」といった
問題が起きたとき、`if` 文でチェックしてメッセージを表示する、という
書き方が中心でした。しかし実際のシステムでは、エラーが起きたときに

- どこで、どんな種類のエラーが起きたのかをプログラムの構造として
  はっきり区別したい
- 画面には詳細を出さず、あとから調査できるようにログに残しておきたい
- エラーが起きても起きなくても、「後片付け」の処理だけは必ず実行したい

といった要求が出てきます。これらをまとめて実現するための仕組みが
「例外処理(`try` / `catch` / `finally` / `throw`)」です。

### 1. 独自の例外クラス `ConfigFileNotFoundException` を作る

`RuntimeException`(PHPにあらかじめ用意されている例外クラスの1つ)を
継承した、`ConfigFileNotFoundException` クラスを作ってください。

- コンストラクタは、見つからなかった設定ファイルのパス(`string`型)を
  1つ受け取ります。
- コンストラクタの中で、「設定ファイルが見つかりません: {パス}」のような
  わかりやすいメッセージ文字列を組み立て、`parent::__construct($message)`
  を呼び出して親クラスにメッセージを登録してください。
- 受け取ったパスを、あとから取得できるように `getConfigPath(): string`
  という getter メソッドも用意してください。

### 2. 設定ファイルを読み込む関数 `loadConfig(string $path)` を作る

指定されたパスの設定ファイルを読み込む関数 `loadConfig(string $path): array`
を作ってください。

- `file_exists($path)` を使って、指定したパスにファイルが実際に存在するか
  確認します。
- ファイルが存在しない(`file_exists()` が `false` を返す)場合は、
  `throw` を使って `ConfigFileNotFoundException` を投げてください。
- ファイルが存在する場合は、`parse_ini_file($path, true)` を使って
  ファイルの中身を連想配列として読み込み、その結果を `return` してください。

### 3. `try` / `catch` / `finally` で呼び出し側の処理を実装する

`loadConfig()` を呼び出す側で、`try` / `catch` / `finally` を使って
次のように処理してください。

- `try` ブロックの中で `loadConfig($path)` を呼び出します。成功した場合は、
  読み込んだ設定内容を画面に表示してください。
- `catch (ConfigFileNotFoundException $e)` ブロックでは、
  - 画面には**詳細を表示せず**、「設定ファイルの読み込みに失敗しました」
    のような、利用者向けの簡潔なメッセージだけを表示してください。
  - その代わりに `error_log()` を使い、**発生時刻とエラーの内容**を
    `error.log` というファイルに記録してください
    (`error_log()` の第3引数にファイルパスを指定します)。
- `finally` ブロックでは、成功・失敗にかかわらず**必ず**実行される
  「処理終了」を表すログを、同じく `error_log()` で `error.log` に
  記録してください。

この演習フォルダには、あらかじめ動作確認用のサンプル設定ファイル
`config_sample.ini` が同梱されています(存在するファイルを読み込む
「成功パターン」の確認に使ってください)。一方、`config_missing.ini`
というファイルは**わざと用意していません**(存在しないファイルを
読み込もうとする「失敗パターン」の確認に使います)。

### 4. `ini_set()` / `error_reporting()` で画面表示を切り替える

`ini_set()` と `error_reporting()` を使って、次の2つの設定例を
コメント付きで示してください(コード中には、実際に有効化する設定と、
コメントアウトしたままにする設定の両方を書きます)。

- 開発環境向け: 画面にエラーを表示する設定
  (`ini_set('display_errors', '1')` と `error_reporting(E_ALL)`)
- 本番環境相当: 画面にはエラーを表示せず、検知だけは行う設定
  (`ini_set('display_errors', '0')` と `error_reporting(E_ALL)`)

この演習では、実際には「本番環境相当」の設定を有効にします。

## 実行方法

ターミナル(コマンドライン)で、この演習のディレクトリに移動してから
以下のコマンドを実行してください。

```bash
# 未完成のひな形を実行してみる(エラーにはならず、TODO部分だけ「まだ実装されていません」等と表示されます)
php practice.php

# 模範解答を実行する
php answer.php
```

`practice.php` の中の `// TODO:` と書かれた部分を自分で実装してから、
もう一度 `php practice.php` を実行し、`answer.php` と同じような結果が
出るか確認してみましょう。

構文だけを素早く確認したいときは、次のコマンドも便利です。

```bash
php -l practice.php
```

実行すると、このディレクトリの中に `error.log` というファイルが
作られます(または追記されます)。テキストエディタで開いて、
実際にエラーの内容と時刻が記録されていることも確認してみましょう。

```bash
cat error.log
```

## ヒント

- 独自の例外クラスを作ると、「どんな種類のエラーが起きたか」を
  `catch` で種類分けしやすくなります。`catch (Exception $e)` のように
  なんでも受け止める書き方だと、本来まったく別の原因で起きたエラーまで、
  同じ `catch` ブロックでまとめて処理してしまうことになります。
- `error_log()` を使うと、指定したファイルにエラー内容を書き込めます
  (第3引数でファイルパスを指定します)。書式は
  `error_log(書き込む文字列, 3, ファイルパス)` です。第2引数を `3` に
  すると「指定したファイルに追記する」という意味になります。
- 本番のWebサーバーでは、画面にエラーの詳細を表示すると情報漏えいに
  つながるため、ログに記録して画面には出さないのが鉄則です。
  `ini_set('display_errors', '0')` としつつ、`error_reporting(E_ALL)`
  でエラーの検知自体はきちんと行っておく、という組み合わせを覚えておきましょう。
- `throw` は「ここでエラーが起きた」ことを知らせて、通常の処理の流れを
  中断し、`catch` ブロックまで一気にジャンプさせる構文です。
- `finally` ブロックは、`try` が成功したときも、`catch` で例外を
  捕まえたときも、必ず実行されます。「後片付け」や「処理終了の記録」など、
  結果に関わらず必ずやっておきたい処理を書くのに向いています。

## サーバーエンジニアとの関連

本番サーバーの運用では、「エラーを画面に出さずログに残す」ことが鉄則
であり、この演習はまさにその実務ルールを体験するものです。

- 本番のWebサーバーで、エラーメッセージ(ファイルパス、SQL文、
  内部の変数の値など)をそのまま画面に表示してしまうと、悪意のある
  第三者に「サーバー内部の構成」や「攻撃の手がかり」を教えてしまう
  ことになりかねません。これは実際に多くのセキュリティ事故で
  原因の1つとされてきた、非常によくある落とし穴です。
- そのため、サーバー構築・運用の現場では、
  `display_errors = Off`(画面には出さない)、
  `log_errors = On`(ログには必ず残す)
  という組み合わせを本番環境の基本設定にするのが一般的です。
  この演習の `ini_set()` / `error_reporting()` の使い分けは、
  まさにその設定を体験してもらうためのものです。
- 独自の例外クラス(`ConfigFileNotFoundException` など)を用途ごとに
  用意しておく設計は、「設定ファイルの問題」「データベース接続の問題」
  「外部APIとの通信の問題」のように、原因の種類ごとに対応方法を
  変えたい実務のシステムで広く使われています。
- `error_log()` で時刻付きのログを残しておく習慣は、障害が起きたときに
  「いつ・何が・どの順番で起きたのか」を調査する上で欠かせません。
  実際の本番運用では、`error_log()` の代わりに、より高機能な
  ログ管理ツール(専用のログライブラリや、監視・ログ収集の
  外部サービスなど)を使うことも多いですが、「エラーを記録し、
  画面には出さない」という基本的な考え方は共通しています。

## 発展課題

余裕がある人は、以下にも挑戦してみましょう。

- 「データベースへの接続に失敗した」ことを表す
  `DatabaseConnectionException`(こちらも `RuntimeException` を継承)
  という、もう1つの独自例外クラスを追加してみましょう。
  `loadConfig()` とは別に、たとえば `connectDatabase(array $config)`
  という関数を作り、`$config['database']['host']` が空文字列だった場合に
  この新しい例外を `throw` するようにしてみてください。そのうえで、
  `try` ブロックの中で `loadConfig()` と `connectDatabase()` の両方を
  呼び出し、`catch (ConfigFileNotFoundException $e)` と
  `catch (DatabaseConnectionException $e)` のように、`catch` ブロックを
  複数並べて、エラーの種類ごとに異なるログメッセージを出し分けてみましょう
  (`catch` は1つの `try` に対して複数書くことができます)。
