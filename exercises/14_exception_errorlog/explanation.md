# 解説: 例外処理とエラーログ

## コードの流れ

`answer.php` は大きく5つのパートに分かれています。

1. **画面表示設定(`ini_set` / `error_reporting`)**
   開発環境向けの設定(画面にエラーを表示する)をコメントとして示しつつ、
   実際には本番環境相当の設定(`ini_set('display_errors', '0')` と
   `error_reporting(E_ALL)`)を有効にしています。「エラーの検知はする、
   ただし画面には出さない」という組み合わせが本番運用の基本です。

2. **独自の例外クラス `ConfigFileNotFoundException` を作る**
   PHP標準の `RuntimeException` を継承し、コンストラクタで
   「どの設定ファイルが見つからなかったか」を含むメッセージを組み立てて、
   `parent::__construct($message)` で親クラスに登録しています。

3. **`loadConfig()` 関数(`file_exists` と `throw`)**
   `file_exists($path)` でファイルの存在を確認し、存在しなければ
   `throw new ConfigFileNotFoundException($path);` として例外を投げます。
   存在する場合は `parse_ini_file($path, true)` で設定内容を配列として
   読み込んで返します。

4. **`demoConfigLoad()` 関数(`try` / `catch` / `finally`)**
   `loadConfig()` の呼び出しを `try` ブロックに、失敗時の処理を
   `catch (ConfigFileNotFoundException $e)` ブロックに、そして
   成功・失敗にかかわらず必ず実行したい「処理終了」の記録を `finally`
   ブロックに書いています。`catch` の中では、画面には簡潔なメッセージ
   だけを表示し、詳細なエラー内容と発生時刻は `error_log()` を使って
   `error.log` に記録しています。

5. **実行と、ログ内容の確認表示**
   実際に存在する `config_sample.ini` を読み込む「成功パターン」と、
   わざと用意していない `config_missing.ini` を読み込もうとする
   「失敗パターン」の両方を `demoConfigLoad()` に渡して実行し、最後に
   `error.log` の中身を画面に表示して、正しく記録されたことを確認できる
   ようにしています(この最後の表示は学習用の確認であり、本番環境では
   通常行いません)。

全体を通して、「エラーが起きるかもしれない処理を `try` に囲み、
エラーの種類ごとに `catch` で処理を分け、後片付けを `finally` に書く」
という例外処理の基本の型と、「画面には出さず、ログに残す」という
実務の原則を体験できる構成になっています。

## 重要なポイント(使用した関数・構文の解説)

- **`try` / `catch` / `finally`**
  `try { ... }` の中に、エラーが起きるかもしれない処理を書きます。
  その中で例外が `throw` されると、`try` ブロックの残りの処理は
  すぐに中断され、対応する `catch` ブロックにジャンプします。
  `finally { ... }` ブロックは、`try` が最後まで成功した場合でも、
  `catch` で例外を捕まえた場合でも、**必ず**実行されます。
  「ファイルを閉じる」「後片付けのログを出す」のように、結果に関わらず
  必ずやっておきたい処理を書くのに向いています。

- **`throw`**
  「ここでエラー(例外)が発生した」ことをプログラムに知らせる構文です。
  `throw new ConfigFileNotFoundException($path);` のように、例外オブジェクトを
  `new` で作りながら、その場で `throw` するのが一般的な書き方です。
  `throw` された瞬間、それ以降のその関数内の処理は実行されず、
  呼び出し元をさかのぼって、対応する `catch` ブロックを探しに行きます。

- **`Exception` と、それを継承した独自の例外クラス**
  PHPには、あらゆる例外のもとになる `Exception` クラスと、それを継承した
  `RuntimeException`・`InvalidArgumentException` などが標準で用意されて
  います。`class ConfigFileNotFoundException extends RuntimeException`
  のように、これらを継承して**独自の例外クラス**を作ることができます。
  独自の例外クラスを作る一番のメリットは、`catch` するときに
  「どの種類のエラーだったか」で処理を分けられることです。
  `catch (ConfigFileNotFoundException $e) { ... }` と書けば、
  「設定ファイルが見つからなかった」というエラーだけをピンポイントで
  捕まえられます(それ以外の原因で起きた、まったく別のエラーまで
  誤って捕まえてしまう心配がありません)。

- **`getMessage()`**
  すべての例外(`Exception` とその子クラス)が持っている、
  組み込みのメソッドです。`new クラス名($message)` としたときに
  `parent::__construct($message)` 経由で登録した文字列を、
  あとから `$e->getMessage()` として取り出せます。
  今回は、独自に用意した `getConfigPath()` と組み合わせて使うことも
  できますが、`answer.php` では `getMessage()` だけでログに必要な
  情報(組み立て済みのメッセージ)を十分にまかなえるようにしています。

- **`error_log()`**
  文字列を「どこかのログ」に記録するためのPHP標準関数です。
  `error_log(メッセージ, メッセージの種類, 送り先)` という形で使い、
  2番目の引数(メッセージの種類)を `3` にすると、
  「3番目の引数で指定したファイルに、メッセージを**追記**する」
  という動作になります。
  ```php
  error_log($logMessage . PHP_EOL, 3, LOG_FILE);
  ```
  `error_log()` は改行を自動では付け足さないため、
  複数行のログを見やすく残すには、自分で `PHP_EOL` を付け加える
  必要がある点に注意してください。

- **`ini_set()` / `error_reporting()`**
  `ini_set('設定名', '値')` は、`php.ini` にあるさまざまな設定を、
  プログラムの実行中に一時的に変更するための関数です。
  `display_errors` を `'0'` にすると、PHPが検知したエラーを
  画面に表示しなくなります。一方 `error_reporting(E_ALL)` は、
  「どのレベルのエラーまでを検知の対象にするか」を指定するもので、
  `E_ALL` を指定すると、警告(Warning)や非推奨(Deprecated)の通知まで
  含め、あらゆるエラーを検知の対象にします。
  「`error_reporting(E_ALL)` で検知はするが、`display_errors` は
  `0` にして画面には出さない」という組み合わせが、本番のWebサーバーで
  よく使われる設定です。

- **`file_exists()` / `parse_ini_file()`**
  `file_exists($path)` は、指定したパスにファイル(またはディレクトリ)が
  実際に存在するかどうかを `true`/`false` で返します。
  `parse_ini_file($path, true)` は、INI形式(`[セクション名]` と
  `キー = 値` の組み合わせ)で書かれた設定ファイルを読み込み、
  連想配列に変換してくれる関数です。第2引数を `true` にすると、
  `[app]` のようなセクションごとに配列を分けて読み込みます。

## 初心者がつまずきやすいポイント

- **`catch` の型を指定しすぎて、何も捕まえられない**
  `catch (ConfigFileNotFoundException $e)` は、その型(またはその子クラス)
  の例外だけを捕まえます。もし `loadConfig()` の中で、指定した型とは
  まったく別の例外(たとえば `TypeError` など)が発生した場合、
  この `catch` では捕まえられず、プログラムはそのまま `Fatal error`
  になって終了してしまいます。「本当に想定しているエラーの型を
  `catch` で指定できているか」を意識しましょう。

- **`finally` を「エラーが起きたときだけ実行される」と勘違いする**
  `finally` は、`try` が成功したときも、`catch` で例外を捕まえたときも、
  **どちらの場合でも**必ず実行されます。「エラーが起きなかったときは
  スキップされる」わけではない点に注意してください。

- **`throw` した後の行が実行されると誤解する**
  `loadConfig()` の中で `throw new ConfigFileNotFoundException($path);`
  を実行すると、その関数の残りの行(`parse_ini_file()` を呼び出す行など)
  は一切実行されず、すぐに呼び出し元の `catch` に処理が移ります。
  「`throw` した後にもまだ何か処理を続けたい」場合は、`throw` する前に
  その処理を済ませておく必要があります。

- **独自例外クラスに `__construct` を書き忘れる**
  `class ConfigFileNotFoundException extends RuntimeException` と
  書いただけで中身を空にしておくと、独自のメッセージ組み立てや
  `getConfigPath()` のような追加機能を持てません(それでも
  `RuntimeException` としては動作するので、致命的エラーにはなりません)。
  「独自の情報を持たせたい例外クラスには、コンストラクタを自分で
  定義する」ことを意識しましょう。

- **`error_log()` の第2引数を指定し忘れる**
  `error_log($message)` のように第2引数を省略すると、PHPの設定
  (`error_log` ディレクティブ)に従った送り先(多くの場合はWebサーバーの
  標準のエラーログ)に送られてしまい、今回のように「自分で指定した
  `error.log` というファイルに書き込みたい」という意図どおりには
  なりません。特定のファイルに書き込みたいときは、必ず第2引数に `3`、
  第3引数に書き込み先のパスを指定してください。

## よくあるエラーと対処法

- **`Fatal error: Uncaught ConfigFileNotFoundException: ...`**
  `throw` された例外を、どの `catch` ブロックでも受け止められなかった
  ときに出るエラーです。多くの場合、`catch` の型指定を間違えている
  (`catch (Exception $e)` ではなく、想定と違う型を書いている)か、
  そもそも `try`/`catch` で囲むのを忘れていることが原因です。
  `throw` している例外のクラス名と、`catch` している型が一致しているか
  確認しましょう。

- **`Warning: file_put_contents(...): Failed to open stream`
  (または、`error_log()` に関連する警告)**
  ログファイルを書き込もうとした場所に、書き込み権限がない場合などに
  発生することがあります。この演習では `__DIR__` を使って、
  スクリプト自身と同じディレクトリにログファイルを作るようにしている
  ため、通常は問題になりませんが、権限が特殊な環境で作業している場合は
  ディレクトリの書き込み権限を確認してみてください。

- **`Fatal error: Declaration of ConfigFileNotFoundException::__construct() must be compatible with ...`**
  独自の例外クラスのコンストラクタの引数の型が、継承元
  (`RuntimeException` やその親の `Exception`)のコンストラクタと
  互換性がない場合に出るエラーです。この演習のように、
  「`Exception` 系のコンストラクタとは別に、独自の引数(`$configPath`)を
  受け取り、その中で `parent::__construct($message)` を呼び出す」
  という書き方をしていれば、通常はこのエラーにはなりません。

- **ログファイルの中身が空、または期待した内容と違う**
  `error_log()` を呼び出すタイミングや、渡している文字列の組み立て方
  (`sprintf()` の書式や変数名)を見直してみましょう。特に、
  `date('Y-m-d H:i:s')` の実行結果を変数に入れ忘れて、
  関数そのものを文字列として埋め込んでしまう、といった単純な書き間違いが
  よくある原因です。

## まとめ

- `try` / `catch` / `finally` を使うと、「エラーが起きるかもしれない処理」
  「エラーが起きたときだけの処理」「結果にかかわらず必ず行う処理」を、
  それぞれ役割ごとに分けて書くことができます。
- `Exception`(や `RuntimeException` などその仲間)を継承した独自の
  例外クラスを作ると、`catch` する際に「どんな種類のエラーが起きたか」で
  処理を分けやすくなり、コードの意図も伝わりやすくなります。
- `throw` は、通常の処理の流れを中断して、対応する `catch` ブロックまで
  一気にジャンプさせる構文です。
- `error_log()` を使うと、エラーの内容や発生時刻を指定したログファイルに
  記録できます。第2引数を `3`、第3引数に書き込み先のパスを指定するのが
  ポイントです。
- 本番のWebサーバーでは、`display_errors` を無効にしてエラーの詳細を
  画面に表示せず、その代わりに `error_log()` などでログにしっかり
  記録しておく、という運用が鉄則です。この演習で体験した
  「画面には出さず、ログに残す」という考え方は、実際のサーバー運用や
  セキュリティ対策の基本になる、とても重要な原則です。
