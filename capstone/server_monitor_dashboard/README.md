# Capstone: シンプルなサーバー監視ダッシュボード

## これは何か(概要)

このプロジェクトは、`exercises/01_variables_datatypes/` から
`exercises/16_log_analyzer/` までの16本のPHP基礎演習で学んだ内容を、
1つのCLI(コマンドライン)アプリケーションとして**統合したポートフォリオ作品**です。

演習では「変数」「配列」「関数」「文字列」「日時」「ファイルI/O」
「CSV/JSON」「オブジェクト指向」「例外処理」「サーバー情報取得」
「ログ解析」といったテーマを、それぞれ独立した小さなスクリプトとして
1つずつ練習してきました。しかし実際の業務システムやツールは、
こうした個々の技術を組み合わせて初めて意味のあるアプリケーションになります。

このcapstone(集大成)プロジェクトでは、「サーバー監視ダッシュボード」という
1つの題材を通して、それらの技術を実際に組み合わせて動かす体験をします。
Webサーバーやデータベースサーバーは一切不要で、`php dashboard.php`という
1つのコマンドだけで、これまでの学習内容を横断した動作を確認できます。

## この作品で統合されている演習内容

| このプロジェクトの機能 | 対応する演習 | 使われている主な技術 |
| --- | --- | --- |
| `Server` クラスでサーバー1台分の情報をモデル化 | 演習13(OOPの基礎) | クラス・プロパティ・カプセル化・静的メソッド |
| `config.json` から監視対象サーバー一覧を読み込む | 演習09(CSV・JSON操作) | `json_decode()`、連想配列 |
| PHP実行環境(バージョン・ディスク・負荷)の取得 | 演習15(サーバー情報取得) | `phpversion()`、`disk_free_space()`、`sys_getloadavg()` など |
| `access.log` の簡易集計(ステータス別・IPランキング) | 演習16(簡易ログ解析ツール) | 正規表現(`preg_match()`)、配列によるカウンタ、`arsort()` |
| 設定ファイル・ログファイルの異常を検知して記録 | 演習14(例外処理とエラーログ) | 独自例外クラス、`try`/`catch`、`error_log()` |
| ダッシュボード表・HTMLレポートの整形表示 | 演習04〜06(配列・関数・文字列) | `foreach`、関数化、`sprintf()`、`mb_strwidth()` |
| `report.html` の書き出し | 演習08(ファイルI/O) | `file_put_contents()` |

このように、1つ1つの演習で身につけた「部品」を、`Server`クラスと
`Monitor`クラスという2つのクラスの中で組み合わせて、
1つの完成したツールに仕上げています。

## ディレクトリ構成

```
capstone/server_monitor_dashboard/
├── classes/
│   ├── Server.php            … サーバー1台分の情報を表すクラス
│   ├── Monitor.php           … 実行環境・サーバー一覧・ログ集計をまとめる司令塔クラス
│   ├── ConfigException.php   … 設定ファイル(config.json)関連の独自例外
│   └── LogFileException.php  … アクセスログ(access.log)関連の独自例外
├── config.json                … 監視対象サーバー(ダミー)4台分の設定ファイル
├── access.log                  … ダミーのアクセスログ(Combined Log Format風、15行)
├── dashboard.php                … エントリーポイント(実行するファイル)
├── report.html                  … dashboard.php を実行するたびに自動生成されるHTMLレポート
├── error.log                    … 実行中に問題が起きた場合にのみ生成されるエラーログ
└── README.md                    … このファイル
```

`report.html` と `error.log` は、あらかじめ用意されているファイルではなく、
`dashboard.php` を実行するたびに自動的に(上書き)生成されるファイルです。

## 動作要件

- PHP 8.0 以上(`match` 式(PHP 8.0で追加された構文)を使用していますが、
  `readonly` プロパティ(PHP 8.1で追加)は使っていないため、
  8.0以降であれば動作します)
- Webサーバー・データベースサーバーは**不要**です。CLI(コマンドライン)だけで完結します

## 実行方法

ターミナル(コマンドライン)で、このディレクトリに移動してから
以下のコマンドを実行してください。

```bash
cd capstone/server_monitor_dashboard
php dashboard.php
```

実行すると、次の2つのことが行われます。

1. **コンソールに、罫線付きのダッシュボードを表示する**
   - PHP実行環境情報(PHPバージョン・OS・ディスク容量・ロードアベレージなど)
   - 監視対象サーバー一覧(名前・IP・CPU使用率・メモリ使用率・ステータス)
   - アクセスログ集計(ステータスコード別件数、アクセス数トップ5のIPアドレス)
2. **`report.html` というHTMLファイルを、このディレクトリに書き出す**

構文だけを素早く確認したい場合は、次のコマンドも使えます。

```bash
php -l dashboard.php
php -l classes/Server.php
php -l classes/Monitor.php
```

## 生成されるレポート(report.html)について

`dashboard.php` を実行すると、コンソールに表示したのと同じ内容を、
表組みで見やすく整えた `report.html` というファイルに書き出します。

- ブラウザ(Chrome、Safariなど)で `report.html` を直接開くことで、
  コンソールを開かなくても結果を確認できます
  (メールで送ったり、社内で共有したりする場面をイメージしています)
- サーバーの状態(正常・注意・危険)は、色分けして表示されます
- `htmlspecialchars()` によるエスケープ処理を行っており、
  仮にサーバー名などに `<` や `"` のような記号が含まれていても、
  意図しないHTMLとして解釈されない(クロスサイトスクリプティング対策の)
  作りになっています

`report.html` はGitなどにコミットする必要はありません。実行するたびに
最新の内容で上書き生成される「出力ファイル」です。

## `config.json` のカスタマイズ方法

`config.json` は次のような形式のJSONファイルです。`servers` の配列に
オブジェクトを追加・変更・削除することで、監視対象サーバーの台数や
内容を自由に書き換えて試すことができます。

```json
{
    "servers": [
        {
            "name": "web01",
            "ip": "192.168.1.10",
            "cpuUsage": 42,
            "memoryUsage": 55
        }
    ]
}
```

`cpuUsage` と `memoryUsage` は、どちらか大きいほうの値をもとに
`Server::getStatus()` が次のように状態を判定します。

- 70未満 → 正常
- 70以上90未満 → 注意
- 90以上 → 危険

## 例外処理とエラーログについて

`config.json` が存在しない・JSONとして壊れている場合や、
`access.log` が見つからない場合を、それぞれ `ConfigException` /
`LogFileException` という独自の例外クラスで検知するようになっています。

試しに、`config.json` を一時的にリネームしたり、
中身をわざと壊れたJSON(例: `{invalid`)に書き換えたりしてから
`php dashboard.php` を実行してみてください。

- コンソールには、利用者向けの簡潔なエラーメッセージだけが表示されます
  (内部のファイルパスなどの詳細情報を、画面にそのまま出さないのは、
  実際のサーバー運用でも大切な考え方です)
- 詳細なエラー内容(発生時刻・例外の種類・メッセージ)は、
  同じディレクトリの `error.log` に追記されます
- `config.json` が壊れていても、`access.log` の集計は正常に行われる
  (逆も同様)ように、それぞれの処理を個別の `try`/`catch` で
  囲んでいます。1箇所の異常が原因で、ダッシュボード全体が
  表示できなくなってしまう、という事態を避ける設計です

確認が終わったら、`config.json` をもとの内容に戻すのを忘れないようにしましょう。

## このポートフォリオでアピールできるスキル

このcapstoneプロジェクトを完成させたことで、次のようなスキルを
採用担当者に対して具体的に示すことができます。

- **オブジェクト指向設計の実践力**
  `Server` クラスによるカプセル化、`fromArray()` / `toArray()` といった
  「名前付きコンストラクタ」パターンの活用、`Monitor` クラスによる
  責務の分離(実行環境の取得・設定読み込み・ログ集計をそれぞれ独立した
  メソッドに切り分けている)など、単に動くコードを書くだけでなく、
  **読みやすく・変更しやすい設計**を意識できることを示せます。
- **堅牢なエラーハンドリング**
  「異常が起きたら即座に画面が壊れる」のではなく、独自の例外クラスで
  異常を検知し、利用者には簡潔な案内を、開発者にはログファイルに
  詳細な記録を残す、という**本番運用を意識した設計**ができることを
  アピールできます。
- **外部データ形式(JSON・ログ)の実務的な扱い**
  設定ファイルをJSONで管理し、アクセスログを正規表現で解析するという、
  実際のサーバー運用・監視ツールで日常的に行われている作業を
  一通り経験していることを示せます。
- **CLIツールとしての完結性**
  Webサーバーやデータベースなど外部環境に依存せず、
  `php dashboard.php` の1コマンドだけで結果を再現できる設計にすることで、
  「動作確認のハードルを下げる」という、チーム開発でも重視される
  配慮ができることを示せます。
- **人間にとって読みやすい出力を作る力**
  CLIの罫線付き表と、ブラウザ表示用のHTMLレポートという
  2種類の異なる出力形式を、同じデータ(`Monitor::generateReport()`の
  結果)から作り分けられることを示せます。これは「同じデータを、
  見る人・場面によって適切な形で提示する」という、実務でもよく
  求められる考え方です。

「サーバー構築エンジニア」を目指す方にとっては、これらはまさに
実際の監視ツールや運用スクリプトを開発・保守する際に必要となる
基礎体力そのものです。

## 発展課題(任意)

余裕がある人は、以下にも挑戦してみましょう。

- `Server` クラスを継承した `WebServer` クラス(演習13の発展課題相当)を
  新しく作り、`requestsPerSecond`(1秒あたりのリクエスト数)プロパティを
  追加してみましょう。`config.json` の各サーバーに `"type": "web"` の
  ような種別を持たせ、`Monitor::loadServers()` の中で種別に応じて
  `Server` と `WebServer` を使い分けるように改造すると、
  より実践的なオブジェクト指向設計の練習になります。
- 現在は「CPU使用率とメモリ使用率のうち大きいほう」で状態を判定していますが、
  ディスク使用率もサーバーごとに保持するようにして、
  3つの指標すべてを考慮した `getStatus()` に拡張してみましょう。
- `dashboard.php` に、コマンドライン引数(`$argv`)で
  「ステータスが『危険』のサーバーだけを表示する」といった
  フィルタリング機能を追加してみましょう(演習15で学んだ
  `$argv` の使い方が活用できます)。
- `Monitor::analyzeAccessLog()` を、日付ごと・時間帯ごとの
  アクセス数集計にも対応させ、ダッシュボードに「時間帯別アクセス数」の
  セクションを追加してみましょう。
